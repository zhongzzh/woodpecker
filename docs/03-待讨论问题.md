## A. 输入契约：一个任务到底给工具什么？【最优先】

D1 定了"人工提取输入"，那就必须定义清楚提取出来的东西长什么样。
建议做一张固定的**任务卡**，字段草案：

| 字段 | 必填 | 示例 | 说明 |
| --- | --- | --- | --- |
| 任务类型 | 是 | 新增函数 | 新增函数 / 性能优化 / 算法优化 |
| 函数名 | 是 | surfaceArea | 一卡一函数？还是 labeledge+labelnode 同 MR 算一卡？待定 |
| 所属库 | 是 | TyComputationalGeometry | |
| 仓库地址 | 是 | https://git.tongyuan.cc/syslab/packages/math/TyComputationalGeometry.jl | |
| 分支名 | 是 | （MR 的源分支名） | 人工从 MR 页面抄？还是给 MR 链接由工具想办法查？ |
| 文档位置 | 是 | 仓库内路径，或另一 MR 链接 | 覆盖 pagenorm 这种"文档在别的 MR"的场景 |
| 单测位置 | ？ | 仓库内路径 | 若目录约定固定（见 D 项），可自动定位，此字段可省 |
| 性能报告 | 是 | 直接粘贴 note 正文 | 现阶段建议直接贴文本，绕开 API 依赖 |
| 性能标准 | 是 | （待用户提供格式） | |

**待拍板：**

1. 字段有没有缺、有没有多余？
2. 任务卡用什么载体：Markdown 模板文件？YAML？还是对话里直接口述？
   （初步倾向：`tasks/<期号>/<函数名>/task.md`，人填模板、工具读文件——可追溯、可重跑。）

## C. 实现形态：skill / subagent / workflow / 纯脚本【想清楚再选】

比较维度：

| 维度 | 关键问题 |
| --- | --- |
| 交互性 | 哪些步骤必须人确认？（例：缺口清单先人审，通过后再生成用例？） |
| 上下文量 | 一个函数的文档+测试+相关源码有多大？单个对话装不装得下 |
| 并行度 | 一期约 5 个任务，要不要并行跑 |
| 可复现 | 换台机器/换个实习生，能不能照着跑出同样的东西 |
| 失败恢复 | 中途断了，能不能只重跑一个任务而不从头来 |

**初步倾向（未定，仅供讨论）：**

- 确定性步骤（clone/checkout、定位文件、收集材料）→ 脚本，稳定可靠；
- 分析步骤（读文档、找覆盖缺口、写用例、判性能）→ 模型做；
- 载体选型（skill 还是 agent 还是 workflow）等 A、B 定型后再决定——
  只要"输入任务卡、输出报告"这个接口稳定，换载体成本很低，不必现在锁死。

## D. 四个库的目录/命名约定

需要用户各提供一个真实例子（任一函数即可）：

- 函数文档 md 的路径规则？
- 单元测试文件的路径与命名规则？
- 测试怎么组织（runtests.jl 怎么 include？@testset 命名习惯？）

四个库是否一致？不一致就分别记录。
→ 决定 A 项"单测位置"能否自动推导，也直接决定分析的精准度。

## E. 要不要在本机真的跑？【范围上最大的分叉】

三个档位：

1. **纯静态**：只读文档+测试代码做覆盖分析，补充用例只做静态检验（不运行）。
2. **静态 + 回归**：额外在本机跑一遍开发已有的测试（性能优化类任务的回归需要这个）。
3. **静态 + 回归 + baseline**：补充用例的 expected 经 MATLAB（或其他）baseline 验证后回填。

档位越高越可信，但对本机环境（Julia/Syslab 版本、内部 registry、MATLAB）的依赖越重。
**待确认：** 本机有什么环境？用户日常是怎么跑这些库的测试的？
（注：现有 skill 的立场是"补充用例只静态检验、不运行"，但它要求 MATLAB baseline。）
