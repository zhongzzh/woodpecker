# 08 性能优化任务方案

> 状态：方案已实现并完成离线回归，记录于 2026-07-17。
> 示例任务：`【数学库2026.7月第二周周提测】TyDifferentialEquation：ode89 函数性能优化`。

## 1. 目标与范围

Woodpecker 当前已经实现“新增函数”任务。本次增加第二种任务类型：**函数性能优化**。

两类任务继续共用代码 MR 取数、材料快照、历史报告和 Syslab 性能阈值，但下列环节必须分流：

| 环节 | 新增函数 | 性能优化 |
| --- | --- | --- |
| 人工输入 | 任务名 + 代码 MR + 文档 MR | **任务名 + 代码 MR** |
| 文档来源 | 文档 MR 的新增 md | 本地既有 `syslab-docs-2.0` 中的函数文档 |
| 性能参照系 | 分支版 Julia / MATLAB | **分支版 Julia / 基准版 Julia** |
| 主要性能数据 | 分支详细表中的 `execute_time_*_diff` | 最新报告摘要中的“变快/变慢百分比” + 基准/分支 Julia 运行时间 |
| 输出措辞 | 通过 / 不通过 | 每个用法标记【未衰退（性能提升/持平）】或【发生衰退】 |

本方案中的“性能优化”是函数级性能优化。算法优化是否完全复用本流程，仍需拿真实任务确认，
本次不自动把“算法优化”并入该类型。

## 2. 输入契约与任务识别

### 2.1 人工输入

性能优化任务只要求两项：

1. 任务名称，例如：
   `【数学库2026.7月第二周周提测】TyDifferentialEquation：ode89 函数性能优化`；
2. 数学库代码 MR 链接。

**不再要求文档 MR 链接。** 性能优化的函数是既有函数，帮助文档应已存在于：

`C:\Users\TR\Desktop\doc\syslab-docs-2.0`

### 2.2 内部任务类型

后续实现应在任务卡中形成明确的任务类型，而不是让所有步骤重复猜测：

- `new_function`：任务名包含“新增……函数”；
- `performance_optimization`：任务名包含“函数性能优化”或可明确识别的“性能优化”。

`ode89` 应从“`ode89 函数性能优化`”中提取。若任务类型或函数名无法唯一识别，应明确报错，
不能误走“新增函数”的性能算法。

## 3. 材料获取流程

### 3.1 代码侧

代码侧沿用当前只读流程：

1. 打开代码 MR，读取源分支；
2. 取同一 MR 中**报告时间最新**的一条 `julia分支性能对比测试报告`；
3. 本地代码仓库 fetch/checkout/pull 到源分支；
4. 定位函数单元测试与 benchmark；
5. 保存最新性能报告快照，保证结论可以离线复核。

“最新”按报告标题中的时间戳判断，不按页面 DOM 顺序或 note 编号碰运气。

### 3.2 文档侧

性能优化任务不访问文档 MR，改为在固定的本地文档仓库中按函数名定位既有 md：

`syslabHelpSourceCode/projects/<Ty项目>/Doc/.../<函数名>.md`

优先读取 `develop`（或本地可确认对应 `origin/develop`）中的既有文档，避免当前工作区恰好停在
其他新增函数分支时读错版本。后续实现应尽量用只读方式读取指定 revision，不为读取文档而覆盖
用户工作区。

如果本地文档仓库不存在、函数文档重名或没有找到，应在报告中标记“文档未定位”，不能把错误
文件交给 AI，也不应临时要求用户补一个文档 MR 才能启动任务。

### 3.3 功能侧处理

当前方案按以下方式复用已有能力：读取本地既有函数文档与代码分支上的单元测试，继续做静态的
“文档声明 vs 单测覆盖”分析。这里的“功能验证”仍是静态分析，不等同于已经在 Syslab 中执行了
完整回归测试；报告措辞必须保持这一事实。

是否为性能优化任务增加真实回归执行，是后续独立能力，不在本次性能判定规则内。

## 4. 性能报告触发与有效性检查

性能优化判定同时满足以下条件时启动：

1. 当前任务已识别为 `performance_optimization`；
2. 代码 MR 中存在标题含“测试报告”的性能报告，且已选中时间最新的一条；
3. 报告摘要包含“相比于基准版本，分支版本性能变快/变慢了……”一类文本；
4. 报告包含可识别的基准版本和分支版本详细数据，字段至少能够提供：
   - `usage_name`；
   - `j_execute_time_first`；
   - `j_execute_time_average`；
   - `execute_time_first_diff`、`execute_time_average_diff` 等原报告字段，用于结构校验和旁证。

注意：详细表中的 `execute_time_first_diff` / `execute_time_average_diff` 在现有报告结构中表示
**Julia / MATLAB**，不是“分支 / 基准”。性能优化任务不能直接拿这两个字段作为 x。

若只有新增函数式的 Julia/MATLAB 数据而没有基准/分支对比信息，必须报告“无法按性能优化规则判定”，
不能自动回退到新增函数算法。

## 5. 数据模型与字段对应

每个 `usage_name` 分别检查首次、二次两项：

| 检查项 | 参考时间 T | 分支时间 | 摘要变化 | 耗时倍数 x |
| --- | --- | --- | --- | --- |
| 首次 | 基准表 `j_execute_time_first` | 分支表 `j_execute_time_first` | “首次执行时间”百分比 | 分支首次 / 基准首次 |
| 二次 | 基准表 `j_execute_time_average` | 分支表 `j_execute_time_average` | “二次执行时间”百分比 | 分支二次 / 基准二次 |

基准表和分支表按 `usage_name` 配对，不能依赖两张表的行序刚好一致。报告中的 `name` 可作为展示说明，
但不能替代稳定的用法标识。

## 6. 百分比换算与判定算法

### 6.1 摘要百分比换算

设摘要百分比为 y：

- “分支版本性能**变快**了 y%”：`x = 1 - y / 100`；
- “分支版本性能**变慢**了 y%”：`x = 1 + y / 100`；
- 明确“持平”或变化为 0%：`x = 1`。

例如：

| 摘要 | x |
| --- | --- |
| 变快 98.4% | 0.016 |
| 变快 78.5% | 0.215 |
| 变慢 30% | 1.30 |

### 6.2 Syslab 性能判定标准

设参考时间为对应的**基准版 Julia 运行时间** T：

| T | 允许上限 | 衰退条件 |
| --- | --- | --- |
| `T > 1s` | 1.2 倍 | `x > 1.2` |
| `0.1s <= T <= 1s` | 1.25 倍 | `x > 1.25` |
| `T < 0.1s` | 1.5 倍 | `x > 1.5` |

边界规则沿用现有 D16：**x 恰好等于阈值算未衰退，只有 x 大于阈值才算衰退。**

### 6.3 单项、用法与整体结论

- 单项：首次或二次各自套用对应 T 的阈值；
- 单个用法：首次和二次都未超阈值，标记【未衰退（性能提升/持平）】；任一项超阈值，
  标记【发生衰退】；
- 整体任务：任一用法发生衰退，整体性能验证不通过；全部用法未衰退，整体通过。

所有“变快”项的 x 都小于等于 1，因此必然低于三档阈值，结论为未衰退；“变慢”不等于一定衰退，
仍需结合 T 对应的允许上限判断。

## 7. 摘要缺项、舍入与异常数据

用户给出的 ode89 摘要片段写明“共执行 3 个用法”，但只展示了：

- `PerformanceTest1_0` 的二次执行时间：变快 98.4%；
- `PerformanceTest3_0` 的首次执行时间：变快 78.5%；
- `PerformanceTest3_0` 的二次执行时间：变快 98.4%。

这三项换算后分别为 0.016、0.215、0.016，均可判定为未衰退。但该片段没有给出
`PerformanceTest1_0` 的首次、`PerformanceTest2_0` 的首次/二次等数据，所以**仅凭片段不能给
全部 3 个用法下完整结论**。后续工具必须继续读取同一条最新报告的详细表补齐，而不能把“摘要没写”
理解为“持平”或“通过”。

建议采用以下证据优先级：

1. 摘要有百分比：按用户指定公式换算 x；
2. 同时用详细表计算 `x_raw = 分支 Julia 时间 / 基准 Julia 时间` 做一致性校验；
3. 摘要缺某个用法或某个检查项：用两张详细表的 Julia 时间补算 x，并在报告中标记“由详细表补算”；
4. 摘要百分比因一位小数舍入而与原始时间略有差异：保留两者，临界判定优先使用详细表原始时间比值；
5. 基准时间为 0、非数值、字段缺失、同一 `usage_name` 无法配对：标记【无法判定】，不得按通过处理。

报告声明的用法总数、摘要解析出的用法集合、基准表用法集合、分支表用法集合应互相核对；数量或集合
不一致时给出明确告警。

## 8. 推荐报告格式

性能优化报告的性能部分至少包含：

| 用法 | 检查项 | 基准 T(s) | 分支耗时(s) | 报告变化 | x(分支/基准) | 阈值 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| PerformanceTest1_0 | 首次 | … | … | 变快/变慢 y% | … | … | 未衰退 / 发生衰退 |
| PerformanceTest1_0 | 二次 | … | … | 变快/变慢 y% | … | … | 未衰退 / 发生衰退 |

表后逐用法给出聚合标签：

- `PerformanceTest1_0`：【未衰退（性能提升/持平）】；
- `PerformanceTest2_0`：【发生衰退】。

最后给整体结论，并附：最新报告标题/时间、MR 链接、数据是否由摘要直接换算或由详细表补算、
任何缺项/不一致告警。机器人 `perf_status` 继续只作旁证，不替代 Syslab 标准演算。

## 9. 实现影响清单

实现涉及：

1. 任务卡支持 `new_function` / `performance_optimization` 两种类型，`doc_mr` 对后者改为非必填；
2. UI 根据任务类型动态显示必填项，性能优化只显示任务名和代码 MR；
3. 函数名解析支持“`ode89 函数性能优化`”；
4. 文档定位支持从固定本地文档仓库读取既有函数 md；
5. MR 抓取必须完整保留摘要中的每个用法代码块，并继续提取基准/分支两张表；
6. 性能模块拆成两种明确策略：`Julia/MATLAB` 与 `branch/baseline`，禁止混用字段；
7. 性能优化策略按 `usage_name` 配对两表、解析摘要百分比、补算缺项并输出逐用法标签；
8. 总报告、task.json、总结邮件和进度文案适配无文档 MR 的任务；
9. 增加离线回归样例，至少覆盖：全变快、允许范围内变慢、超过三档阈值、摘要缺项、表格错配、
   阈值等号、0/NaN 基准时间。

## 10. 本轮结论

性能优化任务的核心定义是：**取代码 MR 中时间最新的性能报告，以基准版 Julia 时间为 T，
把摘要中的变快/变慢百分比换算为分支/基准耗时倍数 x，再按统一 Syslab 阈值逐项、逐用法判断是否衰退。**

它与新增函数任务共用阈值，但参照系不同；现有 `execute_time_*_diff` 是 Julia/MATLAB 比值，不能直接
复用于性能优化。输入端取消文档 MR，既有文档从本地 `syslab-docs-2.0` 自动定位。
